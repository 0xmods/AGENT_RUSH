AGENT RUSH is a Web3 NFT collection based on 100 original character designs.

The Genesis Season will have:

- 100 unique character artwork designs.
- 8,000 total mintable NFTs.

# 4. CHARACTER EDITION SYSTEM

The collection contains 100 original character designs.

Each character has an edition capacity of 80 NFTs.

Total capacity:

100 characters × 80 editions = 8,000 NFTs.

Different users may own NFTs featuring the same character.

Example:

| Token ID | Character ID | Edition |
|---|---|---:|
| 1 | 001 | 1 |
| 2 | 001 | 2 |
| 3 | 001 | 3 |
| 4 | 002 | 1 |
| 5 | 002 | 2 |

Every NFT must have:

- A unique Token ID.
- A Character ID.
- An edition number.
- A unique owner.
- Its own ERC-721 ownership record.

Multiple tokens can reference the same artwork and character metadata.

## Character metadata

Every character must have:

- Character ID.
- Character name.
- Character description.
- Image URI.
- Character attributes.
- Rarity classification, if applicable.

Every NFT metadata record must additionally identify:

- Token ID.
- Character ID.
- Edition number.
- Collection name.
- Season name.

Do not generate 8,000 separate artwork files.

The project requires 100 original character artwork files, with NFT metadata referencing the appropriate character image.

## Edition management

The smart contract must enforce a maximum of 80 editions per character.

The total number of minted NFTs across all characters must never exceed 8,000.

The contract or its trusted minting mechanism must prevent:

- More than 80 editions of a character.
- Duplicate edition numbers for the same character.
- Invalid Character IDs.
- Minting after the global supply reaches 8,000.

Do not rely only on frontend validation or database counters.

# 5. MINTING SYSTEM – UPDATED RULES

The minting system uses two independent quota mechanisms.

## 5.1 Free mint quota

Every unique, verified Binance `.ai` Agent ID is entitled to one free NFT during Genesis Season.

Rules:

- One free mint per unique Agent ID.
- The free mint can only be used once.
- Transferring an Agent ID to another wallet must not reset its free mint allowance.
- The contract must record the permanent Agent ID identifier associated with the free mint.
- The free mint does not require BNB payment.
- Normal network gas fees still apply.

## 5.2 Paid mint quota

Every wallet address can mint up to nine additional paid NFTs.

Rules:

- Maximum nine paid NFTs per wallet address.
- Price per paid NFT: 0.001 BNB.
- Payment must be checked by the smart contract.
- Incorrect payment must revert the transaction.
- Overpayment handling must be explicitly defined.
- Paid mint counters must be maintained on-chain.
- A wallet must not bypass its paid quota through repeated frontend sessions.

The free mint quota and paid mint quota must be tracked independently.

Important distinction:

The free allowance is Agent ID-based.

The paid allowance is wallet-address-based.

These are separate rules and must not be merged into a single counter.

A person using multiple wallets may be able to access multiple wallet-based paid quotas. Do not claim that the system enforces a strict real-world person-level limit.

## 5.3 Global supply

All free and paid mints consume the same global 8,000 NFT supply.

The system must not reserve an additional supply outside the 8,000 limit unless explicitly approved.

# 6. BINANCE AGENTIC WALLET – QR AUTHENTICATION

This is a mandatory project requirement.

AGENT RUSH must use Binance Agentic Wallet authentication.

Users must connect through the official Binance QR-code authentication and pairing flow.

Do not use generic browser wallet connections as the primary authentication system.

Do not assume that MetaMask, RainbowKit, WalletConnect or a normal injected EVM provider satisfies this requirement.

## Required user experience

1. User opens AGENT RUSH.
2. User selects Connect Binance Agentic Wallet.
3. Website displays an official Binance-supported QR authentication flow.
4. User scans the QR code using the supported Binance application.
5. User approves the pairing.
6. The authentication process is verified.
7. The authenticated Agentic Wallet address is retrieved through the supported official interface.
8. The system verifies the associated Binance `.ai` Agent ID.
9. If both checks succeed, the user can access the mint interface.

## Two independent verification layers

### Layer 1 – Wallet authentication

Verify that the user successfully authenticated through the official Binance Agentic Wallet process.

The authenticated wallet address must come from a trusted, verified authentication result.

Do not trust a wallet address supplied by the frontend.

### Layer 2 – Agent ID verification

Verify that the authenticated wallet is associated with a valid Binance `.ai` Agent ID.

Use the verified registry address, official ABI and supported methods.

Do not invent registry methods or assume an unverified ABI.

Do not assume that a mutable Agent ID display handle is a permanent identity.

Identify a stable Agent ID identifier that can be used for quota tracking.

## Critical integration restriction

The official Agentic Wallet CLI authentication flow and a website QR authentication flow must not be treated as automatically interchangeable.

Before implementation, verify the currently supported Binance Agentic Wallet integration method for third-party websites.

The implementation must establish a secure connection between:

- Binance QR authentication.
- Authenticated wallet address.
- Agent ID verification.
- Transaction-signing wallet.

If the official interface does not support the requested browser flow, report the limitation and propose a verified alternative.

Never implement a simulated QR connection.

# 7. NFT DISTRIBUTION LOGIC

The Genesis Season must support 100 characters with 80 editions each.

The AI development agent must inspect the existing mint logic and recommend the simplest secure distribution mechanism.

Possible approaches:

### Option A – User selects a character

Users can select from available character designs.

Each character can be minted up to 80 times.

Advantages:
- Users can choose their preferred character.
- Easy to understand.
- Clear remaining edition counts.

Disadvantage:
- Popular characters may sell out earlier.

### Option B – Automatic character assignment

The contract assigns the next available character.

Advantages:
- Simpler collection distribution.
- Easier to control edition allocation.

Disadvantage:
- Users cannot directly choose their preferred character.

Do not implement an insecure pseudo-random mechanism and describe it as verifiably random.

For the initial MVP, prefer a transparent distribution method that can be tested and audited.

The final choice must be documented before implementation.
