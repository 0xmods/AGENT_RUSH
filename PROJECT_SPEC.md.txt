# 1. PROJECT OVERVIEW

AGENT RUSH is a Web3 NFT minting and gamification platform designed specifically for users who own a Binance Agent ID.

The main idea is to create an ecosystem where Binance Agentic Wallet users can mint unique meme-themed NFTs, collect different characters, participate in missions, compete on seasonal leaderboards, and earn rewards through participation.

AGENT RUSH is not intended to be a traditional NFT marketplace or an automated trading bot.

It is a **Mint-to-Play Web3 ecosystem** combining:

- NFT minting.
- Binance Agent ID verification.
- AI Agent interaction.
- Meme character collection.
- NFT rarity and evolution.
- Seasonal missions.
- Leaderboards.
- Community rewards.
- NFT marketplace functionality in a later development phase.

The experience should be simple enough for users without blockchain development knowledge.

The platform should also support AI agents that can interact with its smart contracts through Binance Agentic Wallet.

## Main slogan

**MINT YOUR AGENT. JOIN THE RUSH.**

## Main objective

Build a working BNB Chain application where verified Binance Agent ID holders can mint NFTs, manage their collections, participate in activities, and interact with the ecosystem using their AI agents.

# 3. CORE TOKENOMICS AND MINTING MODEL

These are the initial product parameters. They must be configurable or safely adjustable before mainnet deployment.

| Parameter | Initial value |
|---|---|
| Blockchain | BNB Smart Chain |
| NFT Standard | ERC-721 |
| Genesis Supply | 10,000 NFTs |
| First Mint | Free |
| Paid Mint | 0.001 BNB |
| Maximum NFTs per Agent ID | 10 per season |
| Marketplace Fee | 2.5% proposed |
| Royalty | 2.5% proposed |
| Platform Token | None in MVP |

## Strict Participation Model

Only users with a valid Binance Agent ID can participate in minting.

The basic flow:

1. User connects a compatible wallet.
2. The platform checks whether the wallet owns a valid Binance Agent ID.
3. If the user does not have an Agent ID, minting is disabled.
4. If the user has a valid Agent ID, the platform checks their mint history.
5. The first mint in a season is free.
6. Subsequent mints cost 0.001 BNB each.
7. The maximum is 10 NFTs per Agent ID per season.
8. All mint operations are recorded on-chain.

Important implementation requirement:

Mint limits must be associated with a stable, unique Agent ID identifier, not only the wallet address.

The development agent must investigate whether the official Binance Agent ID registry exposes a stable identifier or token ID suitable for this purpose.

Do not assume that a display name or `.ai` handle is a permanent unique identifier.

If an Agent ID is transferred to another wallet, the mint history must not reset.

The free mint and seasonal limit must also be resistant to wallet changes and identity reuse.

## Genesis Supply

The initial collection has a maximum supply of 10,000 NFTs.

A new season must not automatically increase the Genesis supply.

If future seasons require additional NFTs, they should use separately defined collection contracts or explicitly approved supply extensions.

# 4. REVENUE MODEL

The project should have a transparent revenue distribution system.

Every paid mint generates 0.001 BNB.

The proposed distribution is:

| Allocation | Percentage |
|---|---:|
| Treasury | 35% |
| Season Reward Fund | 25% |
| Liquidity / Reserve | 15% |
| Development | 15% |
| Community | 5% |
| Security and Operations | 5% |
| **Total** | **100%** |

The smart contract should account for these allocations separately.

The project must not describe all collected funds as profit.

Reward funds and liquidity reserves are restricted allocations, not automatically available operating revenue.

## Additional potential revenue

These features are not part of the initial MVP:

- Secondary NFT marketplace fees.
- Partner NFT collections.
- Sponsored missions.
- Premium dashboard features.
- API access.
- Paid collection launch services.

No native platform token should be introduced during the MVP stage.

## Reward Model

The initial reward model should use transparent, pre-funded seasonal reward pools.

Possible activities:

- Complete missions.
- Collect different NFT character types.
- Participate in community events.
- Complete verified on-chain actions.
- Earn achievement badges.
- Compete on leaderboards.

Rewards should not be advertised as guaranteed investment returns.

Avoid last-minter-wins jackpots, random paid-entry prize pools, or similar gambling-like mechanisms in the MVP.

Before any public launch, obtain appropriate legal review for the jurisdictions where the platform will operate.

# 6. SMART CONTRACT ARCHITECTURE

The first release should use a small number of contracts.

Do not build unnecessary complexity before the basic minting system works.

## Contract 1: AgentRush.sol

Main NFT contract.

Responsibilities:

- ERC-721 NFT implementation.
- Agent ID eligibility checks.
- Free mint.
- Paid mint.
- Maximum supply.
- Per-Agent-ID seasonal mint limits.
- Token metadata.
- Mint events.
- Pause functionality for minting.
- Optional ERC-2981 royalty information.

Expected functions:

```solidity
mint(uint256 quantity)

quoteMint(address wallet, uint256 quantity)

remainingMintAllowance(address wallet)

agentIdEligible(address wallet)

tokenURI(uint256 tokenId)

setBaseURI(string calldata newURI)

pauseMint()

unpauseMint()
```

The exact ABI and function names may change during development.

## Contract 2: RevenueRouter.sol

Responsible for distributing paid mint revenue.

Responsibilities:

- Receive payments from the NFT contract.
- Allocate funds according to predefined percentages.
- Maintain separate balances.
- Allow authorized recipients to claim their allocations.
- Emit accounting events.

The router should not allow the owner to arbitrarily redirect existing allocations.

## Contract 3: SeasonManager.sol

This contract can be introduced after the first successful minting MVP.

Responsibilities:

- Season registration.
- Season start and end.
- Seasonal reward accounting.
- Mission configuration.
- Achievement tracking.
- Reward claims.

Mission completion that depends on off-chain activity must use a carefully designed verification mechanism.

Do not trust frontend-only mission completion.

## Contract 4: RewardVault.sol

Responsible for holding pre-funded rewards.

Responsibilities:

- Reward deposits.
- Eligibility verification.
- Claim limits.
- Reward history.
- Season-specific accounting.

Rewards must be funded before they are advertised as available.

## Contract 5: Marketplace.sol

Optional future component.

Responsibilities:

- NFT listings.
- Purchases.
- Marketplace fees.
- Royalty handling where supported.

The MVP does not need a custom marketplace.

# 7. BINANCE AGENTIC WALLET INTEGRATION

This is one of the most important parts of AGENT RUSH.

The platform should support users who want their AI agents to interact with AGENT RUSH.

The integration must be based on the official Binance Agentic Wallet developer documentation and supported CLI/API interfaces.

Do not assume that Binance Agentic Wallet automatically behaves like a standard browser wallet provider.

## Two interaction methods

### Method A: Browser Wallet

The user connects a compatible EVM wallet through the website.

The frontend:

1. Connects the wallet.
2. Checks the network.
3. Reads the Agent ID registry.
4. Checks the user's mint allowance.
5. Calculates the required payment.
6. Requests a wallet signature.
7. Sends the mint transaction.
8. Displays the transaction result.

### Method B: Binance Agentic Wallet

The user instructs an AI agent to mint an NFT.

Example user instruction:

```text
Connect to AGENT RUSH.

Check my Binance Agent ID.

Check whether I have a free mint available.

If a free mint is available, mint one NFT.

Otherwise, calculate the paid mint price.

Show me the transaction details and wait for my approval.

Do not spend more than the amount I explicitly approve.
```

The AI agent should:

1. Read the current wallet status.
2. Read the Agent ID.
3. Verify eligibility.
4. Read the contract state.
5. Calculate the mint price.
6. Prepare the transaction.
7. Preview the transaction if supported.
8. Ask for user confirmation.
9. Execute the transaction using the official supported wallet interface.
10. Verify the transaction receipt.
11. Report the minted NFT ID.

## Agentic Wallet Security

- Never request or expose the user's private key.
- Never place private keys in frontend code.
- Never transmit wallet credentials to the AGENT RUSH backend.
- Never execute paid transactions without explicit authorization.
- Never assume an AI agent's response proves that a transaction succeeded.
- Verify successful transactions using the blockchain.
- Use transaction previews where supported.
- Respect wallet spending limits and authorization policies.

## Agent Skill File

Create a dedicated file:

`agent-skill/AGENT_RUSH_SKILL.md`

This file should explain to an AI agent:

- How to identify the AGENT RUSH contract.
- How to read the BNB Chain network.
- How to verify Agent ID ownership.
- How to calculate mint costs.
- How to check mint allowance.
- How to prepare a mint transaction.
- How to obtain explicit user confirmation.
- How to verify transaction results.

The skill must use actual supported Binance Agentic Wallet commands or APIs.

Do not invent CLI commands or pretend unsupported integrations exist.

The AI development agent must follow these rules.

1. Never deploy untested smart contracts to mainnet.
2. Never request the owner's seed phrase or private key.
3. Never put private keys in source code.
4. Never commit `.env` files to GitHub.

6. Use OpenZeppelin libraries instead of implementing standard token functionality from scratch.
7. Test all payment and mint restrictions.
8. Prevent Agent ID transfer or identity changes from resetting mint limits.

11. Use a multisig wallet for important administrative operations in production.
12. Keep reward funds separate from operating funds.
13. Make revenue allocations publicly verifiable.
14. Keep existing NFT transfer functionality available even if new minting is paused.
15. Never silently change contract addresses or network settings.
16. Ask for approval before any transaction involving real funds.
17. Do not fabricate transaction success.
18. Do not use fake blockchain data in the production interface.
19. Clearly distinguish testnet and mainnet.
20. Do not implement unverified Binance Agent ID registry interfaces.
